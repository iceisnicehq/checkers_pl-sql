1 Объект испытаний

**Уровень сложности: 4.3 На отлично**

Обеспечить серверную реализацию классических шашек с ведением партий, историей и рейтингами. Взаимодействие происходит через SQL-клиенты: чтение/запись строк, чтение представлений/отчётов и получение текстовых сообщений. GUI отсутствует.

**Основные требования:**

1. **Создание партии** в базовом режиме (русские 8×8), **2 игрока PvP**, а также **PvE** (против ИИ) и **режим задач** (Puzzle).

2. **Выполнение валидных ходов** с проверкой правил: обязательное взятие, максимальный маршрут, превращение, многократные взятия, пат/матч-финиши.

3. **Параметры партии** при создании:
   - вариант правил: русские 8×8 / международные 10×10;
   - лимит на ход (например, 60 с) и/или лимит на партию (шахматные часы);
   - порог ничьей N полуходов без взятий, включение/выключение повтора позиции как основания ничьей.

4. **Протокол партии** (хронологический список ходов и событий).

5. **История** партий и **топ** игроков по метрике «успех = победы / поражения».

6. **Режим задач/задачника**: старт из произвольной позиции (валидатор валидности позиции), учёт решения (время/число ходов).

7. **Ежедневная позиция** (Daily) с общим идентификатором дня и таблицей результатов.

8. **Серии/матчи**: best-of-N с чередованием цвета, суммарный результат.

9. **Рейтинги** (локальные) по итогам матчей/серий, сезонные таблицы.

10. **PvE**: игра против сервера с уровнями сложности (Easy, Medium, Hard).

11. **Доступ «наблюдателя»** (только чтение статуса/протокола по активным партиям).



2 Требования к программе

2.1 Общие требования

- Отчуждаемость исходного кода.

- Устойчивость к некорректным действиям пользователей.

- Корректная поддержка одновременного обращения большого количества пользователей (больше, чем может одновременно участвовать в одной игровой сессии).

- Под одним пользователем одновременно может быть запущена только одна игровая сессия. При попытке запустить вторую должно быть корректное предупреждающее сообщение.

- При длительном простое игровая сессия должна автоматически корректно завершаться.



2.2 Функциональные требования

2.2.1. Регистрация и аутентификация игроков

В рамках данной реализации мы будем использовать уже существующих пользователей Oracle. Для обеспечения их доступа к игре будет создана специальная роль, включающая все необходимые привилегии. Игроки автоматически создаются при первом обращении к системе через функцию `get_or_create_player_id`.



2.2.2. Создание и старт новой игры

Задача: Реализовать функциональность для создания новой игры между двумя игроками, против ИИ или задачи.

**PvP игра (против игрока):**
- Создание открытой игры (статус 'O') для присоединения любого игрока.
- Создание вызова конкретному игроку (статус 'C').
- Определение начальной позиции доски в зависимости от правил (русские 8×8 или международные 10×10).
- Установка параметров игры: лимиты времени, правила ничьей.

**PvE игра (против ИИ):**
- Создание игры с указанием сложности ИИ ('E', 'M', 'H').
- Автоматическое определение цвета игрока и ИИ.
- Автоматический первый ход ИИ, если он играет за белых.

**Режим задачи (Puzzle):**
- Создание игры из произвольной позиции доски.
- Установка цели задачи (победа или ничья).
- Установка оптимального количества ходов для решения.
- Автоматическое создание ежедневной задачи, если она отсутствует.

**Ежедневная задача (Daily Puzzle):**
- Автоматическое создание задачи дня при первом обращении.
- Выбор задачи из базы, которая не использовалась в последние 30 дней.



2.2.3. Реализация игрового поля

Задача: Создать структуру поля для каждого варианта правил (8×8 или 10×10).

- Каждое поле представлено строкой символов: 'w'/'W' (белые простая/дамка), 'b'/'B' (черные простая/дамка), '+' (пустое поле).
- Позиция доски хранится в сжатом формате (RLE-кодирование) для экономии места.
- Поддержка преобразования координат: нотация (например, 'a1', 'h8') ↔ линейный индекс.
- Визуализация доски в текстовом формате с координатами для отображения пользователю.



2.2.4 Обработка ходов игроков

Задача: Реализовать логику ходов в игре с проверкой всех правил.

**Валидация хода:**
- Проверка формата нотации хода (например, 'a3-b4' для тихого хода, 'c3:e5:g7' для взятия).
- Проверка очереди хода (игрок может ходить только в свой ход).
- Проверка обязательного взятия: если есть взятия, тихий ход запрещен.
- Проверка максимального взятия: для международных шашек обязательно максимальное количество фигур.
- Проверка легальности хода: фигура может двигаться только по правилам.

**Применение хода:**
- Удаление фигуры со стартой позиции.
- Удаление срубленных фигур (при взятии).
- Проверка превращения в дамку:
  - Русские шашки: превращение происходит немедленно при достижении последней горизонтали, даже во время многоходового взятия.
  - Международные шашки: превращение происходит только при остановке на последней горизонтали.
- Установка фигуры на новую позицию.

**Обновление состояния игры:**
- Сохранение хода в таблицу `game_moves`.
- Обновление позиции доски в таблице `games`.
- Передача хода следующему игроку.
- Обновление времени игроков (шахматные часы).



2.2.5 Проверка условий завершения игры

Задача: Реализовать проверку всех условий завершения игры.

**Победа:**
- У противника не осталось фигур.
- Противник заблокирован (нет легальных ходов).

**Ничья:**
- По соглашению сторон (явное предложение и принятие).
- По лимиту полуходов без взятий (если установлен `draw_moves_limit`).
- По повтору позиции (если включен `enable_pos_rep_draw`).
- Для задач с `end_board_state`: достижение целевой позиции.

**Таймаут:**
- Истечение времени на ход (`time_limit_move_sec`).
- Истечение времени на партию (`time_limit_game_sec`) - время одного из игроков истекло.

**Сдача:**
- Явная сдача игрока через `resign_game`.
- Сдача во всем матче (если игра является частью матча).

**Обновление после завершения:**
- Обновление статуса игры ('V', 'D', 'T', 'R').
- Определение победителя.
- Обновление рейтингов игроков (для PvP игр и успешно решенных задач).
- Закрытие сессий зрителей.



2.2.6 Реализация действий после завершения игры

Задача: После завершения игры обновить статистику игроков и обработать матчи.

**Обновление рейтингов:**
- Победа в обычной PvP игре: +16 очков победителю, -16 очков проигравшему.
- Решение задачи (первый раз, только общие задачи): +5 очков.
- Ничья: рейтинг не меняется.
- Минимальный рейтинг: 0 (не может быть отрицательным).

**Обработка матчей:**
- Подсчет побед каждого игрока в матче.
- Проверка завершения матча: для "best of N" нужно выиграть (N+1)/2 игр.
- Создание следующей игры в матче, если матч не завершен.
- Обновление рейтинга после завершения матча: +16 за победу в игре, -16 за поражение, +10*N бонус за матч (N = games_to_win).

**Обновление статистики:**
- Запись времени завершения игры.
- Подсчет общего количества ходов.
- Определение причины завершения (победа, ничья, таймаут, сдача).



2.2.7 Реализация матчей (best-of-N)

Задача: Реализовать систему матчей из нескольких игр.

**Создание матча:**
- Создание записи в таблице `matches` с указанием количества игр для победы (должно быть нечетным).
- Создание первой игры матча с вызовом конкретному игроку.
- Связывание игры с матчем через `match_id`.

**Присоединение к матчу:**
- Принятие вызова через `join_match`.
- Автоматический переход игры в активный статус.

**Продолжение матча:**
- После завершения каждой игры проверка необходимости создания следующей.
- Чередование цвета игроков в каждой следующей игре.
- Автоматическое создание следующей игры с теми же параметрами.

**Завершение матча:**
- Определение победителя матча по количеству побед.
- Обновление рейтингов обоих игроков.
- Установка статуса матча в 'C' (Completed).



2.2.8 Реализация режима задач (Puzzles)

Задача: Реализовать систему задач с произвольными позициями.

**Создание задачи:**
- Валидация позиции доски: проверка корректности формата и расположения фигур на темных клетках.
- Установка цели задачи: победа (уничтожение противника или блокировка) или ничья (достижение `end_board_state`).
- Установка оптимального количества ходов для решения.
- Установка сложности задачи ('E', 'M', 'H').
- Сохранение решения задачи (опционально).

**Ежедневная задача:**
- Автоматический выбор задачи из базы при первом обращении за день.
- Приоритет задачам, которые не использовались в последние 30 дней.
- Создание записи в `daily_puzzles` с привязкой к дате.

**Решение задачи:**
- Проверка достижения цели задачи.
- Подсчет количества ходов, сделанных игроком.
- Сравнение с оптимальным решением.
- Обновление рейтинга при успешном решении (только для общих задач, первый раз).



2.2.9 Реализация игры против ИИ (PvE)

Задача: Реализовать интеллектуального противника с различными уровнями сложности.

**Уровни сложности:**
- Easy ('E'): глубина поиска 4, вероятность случайного хода 25%.
- Medium ('M'): глубина поиска 4.
- Hard ('H'): глубина поиска 6.

**Алгоритм выбора хода:**
- Использование алгоритма Minimax с Alpha-Beta отсечением.
- Оптимизация: приоритет обязательным взятиям, ходам с превращением в дамку.
- Ранний возврат при единственном обязательном взятии.

**Автоматический ход ИИ:**
- ИИ делает ход автоматически после хода игрока.
- Ход выполняется через ту же процедуру `p_process_move` для обеспечения валидности.
- Отображение хода ИИ в протоколе игры.



2.2.10 Реализация режима наблюдателя

Задача: Реализовать возможность просмотра активных игр без участия.

**Присоединение к просмотру:**
- Создание записи в таблице `spectators` при вызове `print_active_board` для чужой игры.
- Автоматическое отображение доски и статуса игры.

**Отображение информации:**
- Текущая позиция доски.
- Информация об игроках и их времени.
- Текущий ход и очередь.
- Информация о матче (если игра является частью матча).

**Выход из просмотра:**
- Явный выход через `stop_spectating`.
- Автоматическое закрытие при завершении игры.



2.2.11 Реализация просмотра реплеев

Задача: Реализовать возможность просмотра завершенных игр пошагово.

**Инициализация просмотра:**
- Создание последовательности для отслеживания текущего хода в реплее.
- Загрузка всех ходов игры из `game_moves`.

**Навигация по ходам:**
- Показ указанного количества ходов за один вызов.
- Возможность перезапуска просмотра с начала через параметр `p_restart`.
- Автоматическая очистка сессии просмотра через 30 минут.

**Отображение:**
- Пошаговый вывод доски после каждого хода.
- Информация о игроке, сделавшем ход.
- Финальное состояние игры с результатом.



2.3 Требования к интерфейсу

2.3.1 Интерфейс для создания игры

Задача: Разработать интерфейс для создания новой игры через процедуру `create_game`.

**Параметры процедуры:**
- `p_opponent_username` - имя оппонента для прямого вызова (PvP) или NULL для открытой игры.
- `p_ai_difficulty` - сложность ИИ ('E', 'M', 'H') для PvE или NULL для PvP.
- `p_player_color` - выбор цвета игрока ('W' или 'B') или NULL для случайного.
- `p_rule_id` - правила игры (1 = русские 8×8, 2 = международные 10×10).
- `p_time_limit_move_sec` - лимит времени на ход в секундах.
- `p_time_limit_game_sec` - лимит времени на партию в секундах (шахматные часы).
- `p_draw_moves_limit` - лимит полуходов без взятий для ничьей.
- `p_enable_pos_rep_draw` - включение ничьей по повтору позиции ('Y'/'N').
- `p_puzzle_id` - ID задачи для решения.
- `p_daily` - создание ежедневной задачи ('Y'/'N').

**Вывод:**
- Текстовое сообщение с ID созданной игры и статусом.
- Автоматический вывод доски для PvE игр и задач.



2.3.2 Интерфейс для отображения состояния игры

Задача: Показывать текущие данные о игре через процедуру `print_active_board`.

**Отображаемая информация:**
- Визуализация доски в текстовом формате с координатами.
- Информация об игроках (имена, цвета).
- Текущий ход и очередь.
- Время игроков (если установлены лимиты).
- Информация о матче (если игра является частью матча).
- Информация о задаче (если это задача).
- Подсветка возможных ходов для активного игрока.

**Параметры процедуры:**
- `p_game_id` - ID игры (опционально, по умолчанию активная игра пользователя).
- `p_username` - имя пользователя для поиска его активной игры (опционально).
- `p_wait_for_turn` - ожидание хода/подключения ('Y'/'N').



2.3.3 Интерфейс для совершения ходов

Задача: Разработать интерфейс для выполнения хода через процедуру `make_move`.

**Формат нотации хода:**
- Тихий ход: 'a3-b4' (откуда-куда).
- Взятие: 'c3:e5' (через двоеточие).
- Многоходовое взятие: 'h4:f6:d8:b6:f2' (через двоеточие).

**Валидация и обработка:**
- Проверка формата нотации.
- Проверка легальности хода.
- Применение хода к доске.
- Автоматический ход ИИ (если это PvE игра).
- Отображение обновленной доски.

**Вывод:**
- Сообщение о принятии хода или ошибке.
- Сообщение о завершении игры (если применимо).
- Сообщение о решении задачи (если применимо).



2.3.4 Интерфейс для управления игрой

Задача: Реализовать интерфейсы для различных действий в игре.

**Сдача в игре:**
- Процедура `resign_game` с параметром `p_resign_match` для сдачи во всем матче.

**Отмена игры:**
- Процедура `cancel_game` для отмены открытой игры или вызова.

**Предложение ничьей:**
- Процедура `draw` с параметром `p_action`:
  - 'O' - предложить ничью.
  - 'A' - принять ничью.
  - 'C' - отменить свое предложение.

**Присоединение к игре:**
- Процедура `join_game` с параметром `p_game_id` для присоединения к открытой игре или принятия вызова.



2.3.5 Интерфейс для работы с задачами

Задача: Разработать интерфейсы для просмотра и создания задач.

**Просмотр списка задач:**
- Процедура `show_puzzles` с фильтрами по сложности и ID задачи.
- Возможность показа решения задачи (если были попытки).

**Просмотр своих задач:**
- Процедура `show_my_puzzles` с фильтром по сложности.

**Создание задачи:**
- Процедура `create_puzzle` с параметрами позиции доски, цели и сложности.

**Удаление задачи:**
- Процедура `delete_my_puzzle` для удаления созданных пользователем задач.

**Ежедневная задача:**
- Процедура `show_daily_puzzle` для просмотра задачи дня.



2.3.6 Интерфейс для работы с матчами

Задача: Разработать интерфейсы для создания и управления матчами.

**Создание матча:**
- Процедура `create_match` с указанием оппонента и количества игр для победы.

**Присоединение к матчу:**
- Процедура `join_match` с параметром `p_match_id`.



2.3.7 Интерфейс для просмотра статистики

Задача: Реализовать представления (views) для просмотра статистики.

**Представления для игр:**
- `v_open_games` - открытые игры.
- `v_active_games` - активные игры со статусом.
- `v_ended_games` - завершенные игры.
- `v_game_protocol` - протокол партии со всеми ходами.

**Представления для матчей:**
- `v_open_matches` - открытые матчи.
- `v_active_matches` - активные матчи.
- `v_ended_matches` - завершенные матчи.
- `v_match_details` - детали матча со всеми играми.

**Представления для статистики:**
- `v_player_history` - история игрока со всеми партиями.
- `v_player_ratings` - рейтинги игроков по сезонам и правилам.
- `v_daily_puzzle_results` - результаты ежедневных задач.
- `v_game_rules` - правила игры.



3 Требования к программной документации

Для проведения всех необходимых проверок должны быть предоставлены следующие материалы:

1) SQL скрипт для развертывания схемы базы данных (таблицы, последовательности, индексы);

2) SQL скрипт для первоначального наполнения базы данных (правила игры, начальные задачи);

3) SQL скрипт для создания пакета, реализующего логику игры (`game_logic.pks` и `game_logic.pkb`);

4) SQL скрипты для создания представлений (views) для статистики;

5) SQL скрипты для создания триггеров и автоматических заданий (schedulers);

6) SQL скрипт для установки прав доступа (роли и привилегии);

7) SQL скрипт, содержащий набор тестовых команд, для проверки ряда пунктов, описанных в разделе 5 данного документа;

8) Документация по использованию (README.md) с описанием всех процедур и представлений.



4 Состав и порядок испытаний

Для проведения испытаний необходим 1 сервер с установленным СУБД Oracle версии не ниже 12-ой, а также хотя бы 2 рабочих места конечных пользователей, с доступом по сети к серверу БД.

На рабочих местах должно быть установлено приложение для доступа к СУБД Oracle, такое как SQL Developer или DBeaver.

Порядок проведения испытания будет следующим:

1) Развертывание БД игры "Шашки" на предоставленном сервере. Для этого необходим пользователь базы данных с правами разработчика.

2) Развертывание пакета с логикой игры на сервере. Для этого необходим пользователь базы данных с правами разработчика.

3) Создание роли, необходимой для предоставления права другим пользователям СУБД на участие в игре. Для этого необходим пользователь базы данных с правами администратора.

4) Создание пользователей, под которыми будет проходить тестирование игры и предоставление им созданной ранее роли. Для этого необходим пользователь базы данных с правами администратора.

5) Проведение позитивного тестирования.

6) Проведение негативного тестирования.

7) Проведение нагрузочного тестирования.

8) Проведение иных проверок.

9) Составление протокола испытаний.
